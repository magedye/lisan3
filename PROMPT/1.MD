# 3. Non-negotiable architectural rules

## 3.1 No direct UI writes to canonical knowledge

The frontend MUST NOT directly mutate canonical semantic knowledge.

All changes must pass through:

`Application Facade`
→ `Command`
→ `Authorization`
→ `Validation`
→ `Domain/Runtime`
→ `Persistence`
→ `Audit`

Queries and derived views remain separate from canonical writes.

---

## 3.2 Separate analysis stage from official status

Do not conflate workflow stages with epistemic states.

Maintain separate concepts such as:

```text
analysis_stage
epistemic_status
review_status
freshness_status
publication_status
```

Example:

```yaml
analysis_stage: FALSIFICATION
epistemic_status: LOCK_BLOCKED
review_status: NOT_REVIEWED
freshness_status: CURRENT
publication_status: PRIVATE_WORKING
```

Never make progression through an analysis workflow automatically grant:

* epistemic lock,
* review approval,
* publication authority,
* owner acceptance.

---

## 3.3 Four status axes remain independent

Preserve:

* Epistemic
* Review
* Freshness
* Publication

A change in one MUST NOT silently change another.

Do not reproduce any prototype behavior that changes all four in one action unless an authoritative backend transition contract explicitly authorizes each change independently.

---

## 3.4 Dynamic registries

Do not hard-code official statuses or Lock Gate counts into frontend/runtime logic.

Resolve them from canonical registries/contracts.

Create or normalize registries as needed for:

* epistemic statuses,
* review statuses,
* freshness statuses,
* publication statuses,
* gate definitions,
* source roles,
* methodology versions,
* corpus profiles,
* tool/skill identities.

---

## 3.5 Authority separation

Developer permission ≠ epistemic authority.

Steward permission ≠ semantic lock authority.

Review approval ≠ publication automatically.

Owner-only transitions must remain owner-only.

Backend authorization must enforce these rules; hiding a button in the UI is insufficient.

---

## 3.6 `{ن ش ز}` fixture rule

Use `{ن ش ز}` only as a reference fixture demonstrating:

`LOCK_BLOCKED / NOT_ESTABLISHED`

unless future canonical evidence and explicit authority legitimately change that state.

Do not make the existing Golden prototype establish a canonical Root Core for `{ن ش ز}` merely to demonstrate a successful flow.

Synthetic fixtures may demonstrate successful lock flows.
