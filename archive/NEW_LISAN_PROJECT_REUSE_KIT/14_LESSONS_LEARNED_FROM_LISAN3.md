# Lessons Learned from Lisan3

## Evidence rule

“Observed” means the repository contains a contract, implementation, test, or durable candidate-bound report supporting the statement. “Recommendation” is this review’s inference for the new project and is not an accepted decision.

## 1. Which controls prevented real classes of error?

**Observed:** exact Tanzil source/hash/identity binding prevented caller-supplied or fixture hashes from becoming canonical; ResearchRun admission rejects unknown/unqualified corpus/method references; Blind Lab blocked prior-semantic reads without falsely declaring contamination; computed Gates reject forged/stale GateReports; QAC field-role quarantine excluded gloss/ontology; graph/vector candidates cannot mutate canonical claims/statuses; the five-root pilot kept Root Core null when exact root/morphology evidence was unavailable. Sources: corpus authority/import tests, run admission, isolation tests, gate/property tests, R1/R2 tests, semantic-pilot report. [TR-104]

**Recommendation:** preserve source/field identity, server-owned execution/state derivation, access receipts, and honest non-resolution. These affect semantic integrity even without Lisan governance.

## 2. Which controls were added because earlier approaches failed?

**Observed:** `LISAN3_HANDOFF.md` records concrete V3 failures: `Base.metadata.create_all()` masked migration drift; API-style Playwright was mislabeled browser E2E; mutation survivors exposed weak freshness/corpus/review tests; snapshots could be marked validated with unknown hashes; Purity dimensions were cosmetically clean; Schemathesis found contract failures; some Hypothesis tests were decorative. Later state records describe targeted remediation. [TR-105]

**Recommendation:** require evidence-type labels and tests that actively kill bypasses. Do not equate a convenient testing substitute with the production property being claimed.

## 3. Which mechanisms became more complex than their value justified?

**Observed:** four status axes, review/publication workflow, Steward, change proposals, gates and derived graph/vector phases serve a governed application. Current semantic progress was still blocked because structural data and seven Purity evaluators were missing. Legacy artifacts also carry repeated owner/release fields and multi-layer presentation ceremony. [TR-106]

**Recommendation:** keep only result strength, completeness, verification, source integrity and revision lineage initially. Add publication/governance workflows after a demonstrated consumer requires them.

## 4. Which decisions should be made earlier when rebuilding?

**Observed:** the active runtime still has verse-level occurrences, while the methodology expects root/lemma/form/construction coverage; the Purity contract later specifies the missing token/segment boundary. Terminology such as Root Core/Definition/Meaning/Concept exists across method and schemas without a complete active terminology registry. [TR-107]

**Recommendation:** decide terminology, exact Quran identity, structural-source role/alignment, lexical-unit/branch model, evidence relations, completeness measures and execution receipts before polishing agents/UI.

## 5. Which components are expensive or dangerous to retrofit later?

**Observed:** Lisan3 required migrations, source-bound methodology revisions, corpus lifecycle separation, status-axis database constraints, OpenAPI/client reconciliation and candidate-bound re-verification after integrity gaps. [TR-108]

**Recommendation:** implement immutable source/protocol/result IDs, token locators, evidence relations, run/execution lineage and source-role separation from the start. These contaminate every downstream result if added late.

## 6. Which components should be deliberately postponed?

**Observed:** the tooling contract deliberately defers LangGraph, Neo4j, Qdrant Server, external RAG frameworks, DSPy, formal tools and observability platforms until specific triggers. Lisan3’s vector benchmark blocked model adoption despite installed sqlite-vec. [TR-109]

**Recommendation:** defer vector/graph infrastructure, optimization, multi-provider proxy, publication workflow, formal verification and distributed services until the core root/local-meaning experiment reveals a need.

## 7. Where did AI autonomy help?

**Observed:** the canonical method assigns AI useful work in hypothesis generation, candidate neighbors, differentiation, counterevidence, falsification support, synthesis and explanation. Pydantic AI demonstrates structured proposal generation and trace storage with a fake provider. [TR-110]

**Recommendation:** grant AI the new project’s intended semantic decision role, but bind each decision to resolved evidence, alternatives, counterevidence, completeness and receipts.

## 8. Where did excessive AI autonomy cause risk?

**Observed:** repeated anti-patterns prohibit dictionary-first reasoning, context leakage, structural overpromotion, generic definitions, forced unity, neighbor cherry-picking, simulated tools, invented statuses and silenced counterevidence. The runtime therefore isolates prior semantics and prevents AI proposals from mutating state. [TR-111]

**Recommendation:** relax proposal-only authority, not evidence reality. AI may prefer a meaning; it may not create witnesses, parser results, source roles, tool receipts or independent-verification status.

## 9. Where did excessive governance slow useful semantic work?

**Observed:** five real ResearchRuns had verified Quran text and clean isolation yet could not progress because exact structure and all Purity evaluations were mandatory for Internal Lock. The corrective addendum separated genuine enabling gaps from a non-gating ROOT_CARD/TERM_CARD request. [TR-112]

**Recommendation:** make diagnostics affect strength/completeness/warnings proportionally. Reserve hard invalidation for fabricated source/tool evidence, prohibited source laundering, circular sole support and unresolved target identity.

## 10. Which concepts look elegant in documentation but provide little practical value?

**Observed:** the documented EvidenceResolver/R3 flow is valuable but not implemented; current Root Definition/Meaning/Concept/Abstract Core fields can overlap; current reproduction manifest endpoint includes static simulated tool/model declarations; active JSON registry/schema directories are empty; the QAC alignment service comments that it should fail closed but currently tolerates missing tokens in fixture behavior. [TR-113]

**Recommendation:** require an executed consumer/test before treating a named layer, schema field or service as a real capability. Remove redundant result views unless users demonstrably need them.

## 11. Which implementation patterns proved especially robust?

**Observed:** immutable hashes and revision-bound manifests; Pydantic `extra="forbid"`; database constraints/listeners; exact source readback; deterministic/idempotent imports; computed gate validity; fixture/fake labels; rebuildable derived indexes; run/space scoping; stale invalidation; negative/property/mutation tests; candidate-bound reports. [TR-114]

**Recommendation:** reuse these patterns selectively at the trust boundaries, with a much smaller domain model.

## 12. Which assumptions should be explicitly re-tested?

**Observed assumptions needing re-test:** one stable root core; usefulness of all six embedding spaces; effectiveness of same-model Agent separation; practical enforceability of pretrained-knowledge isolation; value of eight Purity dimensions as a unified gate; need for graph projection; usefulness of Definition/Meaning/Concept as separate fields; adequacy of Quran-internal evidence for every semantic question; QAC suitability/licensing; and whether Gem/Opal can enforce/export required provenance. [TR-115]

**Recommendation:** turn each into a bounded experiment with a failure criterion before architecture adoption.

## Concise retrospective

The most important Lisan3 achievement is not its governance vocabulary; it is the refusal to let convenient representations impersonate evidence. The most important warning is that sophisticated lifecycle and UI machinery cannot compensate for missing token-level structure, incomplete semantic evaluators and absent real-world semantic benchmarks. [TR-116]
