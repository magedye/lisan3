# 1. الرؤية التصميمية (المبادئ الستة الحاكمة)

1. **البحث قبل الإجابة:** المنتج لا يفترض أن لكل سؤال جواباً جاهزاً. إذا كانت المعرفة غير كافية، فإن **«الأدلة الحالية غير كافية» (`INSUFFICIENT_EVIDENCE`)** هي النتيجة الطبيعية والصحيحة.
2. **الشفافية المعرفية:** يستطيع المستخدم الانتقال دائماً عبر السلسلة: `النتيجة → الأدلة → التشغيل البحثي → corpus → المنهجية → القرار → التاريخ`.
3. **الإفصاح التدريجي (Progressive Disclosure):** تُعرض للمستخدم العام النتيجة وسببها الأساسي، بينما يستطيع المتخصص فتح الأدلة والفرضيات والبوابات والتبعيات.
4. **لا كتابة مباشرة في المعرفة القانونية:** جميع العمليات المؤثرة تمر عبر `Application Facade / Commands / Authorization / Validation`، ولا تكتب الواجهة مباشرة في Canonical Knowledge.
5. **الفصل بين التحقيق واليقين:** لا تُعرض نسبة ثقة (مثل 87%). تُعرض بدلاً منها حالة المعرفة، البوابات، اكتمال التحقيق، والأدلة الناقصة.
6. **العربية أصل التصميم:** التطبيق RTL من الأساس، وليس واجهة LTR مترجمة.

# 2. نموذج المستخدمين والصلاحيات

تكون المنصة واحدة، وتظهر الوظائف وفق الصلاحيات والسياق:

| الدور | الوظيفة | الصلاحيات الأساسية |
| :--- | :--- | :--- |
| **الباحث** | السؤال، الاستكشاف، تشغيل الأبحاث المصرح بها | قراءة النتائج، إنشاء Research Runs، حفظ الأبحاث |
| **الباحث المتخصص** | تحليل الأدلة، الفرضيات، الجيران، والنقاء المنهجي | قراءة متقدمة، تشغيل المختبر المعزول، عرض التفاصيل الكاملة |
| **المراجع البشري** | مراجعة الحالات التي تتطلب حكماً بشرياً | تغيير `REVIEW_STATUS`، التعليق، طلب تغييرات |
| **Steward** | التقاط المعرفة وتحويل أوامر المستخدم إلى Commands محكومة | إنشاء أوامر، عرض Preview، تنفيذ الأوامر المسموح بها |
| **المطور/المدقق** | العقود، traces، JSON، الاختبارات وإعادة الإنتاج | الوصول الكامل للبيانات التقنية، تشغيل الاختبارات، عرض JSON الخام |
| **المالك/سلطة القرار** | القرارات التي يحدد العقد أنها Owner-only | منح `OWNER_ACCEPTED`، تغيير القواعد الحاكمة، إصدار النتائج |

**قاعدة أساسية:** المطور لا يحصل على سلطة معرفية لمجرد كونه مطوراً. و Steward لا يستطيع قفل Root Core من أمر مستخدم حر.

# 4. الغلاف العام للتطبيق (Global Shell)

### 4.1 شريط التنقل الرئيسي
- يوضع في الجهة اليمنى (RTL).
- يعرض فقط المجالات التي تسمح بها صلاحيات المستخدم.

### 4.2 شريط السياق المعرفي (Epistemic Context Strip)
يظهر أعلى كل مساحة موضوع:
- **الجذر:** `{ك ت ب}`
- **المنهجية:** `V7.3`
- **Corpus:** `CANON-001`
- **الحالة المعرفية:** `LOCK_INTERNAL_RESULT`
- **المراجعة:** `NOT_REVIEWED`
- **الحداثة:** `CURRENT`

### 4.3 المفتش السياقي (Contextual Inspector)
لوحة جانبية قابلة للفتح لأي عنصر. تعرض:
- الهوية، النوع، المصدر، الإصدار، الأدلة، التبعيات، البصمة (`provenance_hash`)، وسبب الحالة الحالية.

# 5. النموذج الصحيح لعرض الحالة (المحاور الأربعة)

لا يُستخدم سلم واحد للنضج. تُعرض أربعة محاور مستقلة:

| المحور | الحالات الممكنة |
| :--- | :--- |
| **الحالة المعرفية (Epistemic)** | `OBSERVATION`, `HYPOTHESIS`, `TESTED`, `SUPPORTED`, `LOCK_BLOCKED`, `LOCK_INTERNAL_RESULT`, `REJECTED`, `UNRESOLVED` |
| **حالة المراجعة (Review)** | `NOT_REVIEWED`, `REVIEW_REQUIRED`, `IN_REVIEW`, `APPROVED`, `REJECTED`, `OWNER_DECISION_REQUIRED` |
| **حالة الحداثة (Freshness)** | `CURRENT`, `STALE`, `INVALIDATED`, `REVALIDATION_REQUIRED` |
| **حالة النشر (Publication)** | `PRIVATE_WORKING`, `REVIEWABLE`, `PUBLISHABLE`, `PUBLISHED`, `WITHDRAWN` |

**قاعدة UX:** لكل محور (نص، رمز، لون، تفسير مختصر). لا يعتمد المستخدم على اللون وحده.

# 6. المؤشرات البصرية المعرفية

## 6.1 بطاقة الحالة (العنصر الأهم)
```markdown
**الحالة المعرفية:** موقوف عن القفل `LOCK_BLOCKED`
**السبب:** التفريق مع الجار X غير مكتمل.
**الإجراء التالي:** تشغيل اختبار الاستبدال Y.
```

## 6.2 ملف اكتمال التحقيق (Investigation Coverage)
يقاس بمعروف المقام:
- `المواضع المحللة: 12 / 12`
- `الصيغ المفحوصة: 4 / 5`
- `الجيران الحاسمون المفحوصون: 3 / 4`
- `اختبارات الدحض المكتملة: 5 / 7`

**ملاحظة:** `12/12` تعني **اكتمال الفحص**، ولا تعني صحة الفرضية.

## 6.3 ملف الجودة والكفاية (Quality Profile)
لا يُختزل في رقم واحد. يعرض جدولاً للأبعاد:
- تغطية corpus، تغطية الأدلة، اكتمال البحث عن الأدلة المعارضة
- الفصل بين الجذر والصيغة والسياق
- التفريق بين الجيران، الاتساق الداخلي، الاتساق عبر الجذور والآيات
- اكتمال التبعيات، اكتمال provenance والاستشهاد
- الالتزام بالمنهجية، وضوح الحدود والدحض
- عبء التعارضات غير المحسومة، قابلية إعادة الإنتاج
- الثبات عبر التحليلات المتكررة، حالة المراجعة البشرية، الكفاية التفسيرية

## 6.4 كاشف النقاء المنهجي (Methodological Purity Detector) — مستحدث

### 6.4.1 مؤشر النقاء البصري

| الإشارة | المعنى | الإجراء |
| :--- | :--- | :--- |
| 🟢 **نقي منهجياً** | لا توجد علامات تلوث بالموروث | النتيجة جاهزة للمراجعة |
| 🟡 **شبه نقي** | توجد علامات طفيفة تحتاج تحقق | مراجعة بشرية مطلوبة |
| 🟠 **مشكوك فيه** | توجد علامات تلوث واضحة | إعادة تحليل مطلوبة |
| 🔴 **ملوث منهجياً** | تلوث حاسم بالموروث | رفض النتيجة وإعادة التشغيل |

### 6.4.2 أبعاد النقاء الثمانية

| البعد | ما يكشفه | المصدر |
| :--- | :--- | :--- |
| 1. Dictionary-First Detection | هل بدأ التحليل بتعريف معجمي ثم كيّف الآيات؟ | FM-01 |
| 2. Contextual Leakage | هل دخل معنى المفعول/الفاعل/السياق في الجذر؟ | FM-02 |
| 3. Heritage Bias | هل التعريف يطابق المعاجم التراثية بنسبة عالية دون دليل قرآني مستقل كافٍ؟ | قاعدة جديدة |
| 4. Tafsir Contamination | هل دخل تفسير مفسر معين كدليل حاكم؟ | سياسة المصادر |
| 5. Forced Unification | هل تم دمج فرضيات متعارضة قسراً؟ | FM-12 |
| 6. Generic Overextraction | هل التعريف عام جداً (مثل "حركة"، "علاقة")؟ | FM-08 |
| 7. Letter Semantics Overreliance | هل اعتمد على دلالات الحروف كدليل وحيد؟ | FM-06 |
| 8. Circular Confirmation | هل افترض معنى ثم فسّر الآيات به ثم استخدمها كدليل؟ | FM-03 |

### 6.4.3 التكامل مع المختبر المعزول

- **المرحلة 1: الوقاية (Prevention):** المختبر المعزول يمنع الوصول إلى المعاجم والتفاسير *أثناء* التحليل.
- **المرحلة 2: التشخيص (Diagnosis):** بعد القفل، الكاشف يفحص النتيجة *مقارنة* بالموروث (خارج المختبر).

### 6.4.4 التكامل مع مسار الإصدار (Purity Gate)

- 🟢 نقي → مراجعة بشرية → إصدار
- 🟡 شبه نقي → مراجعة بشرية مكثفة → إصدار مشروط
- 🟠 مشكوك فيه → إعادة تحليل → لا إصدار
- 🔴 ملوث → رفض → إعادة تشغيل في Blind Lab

# 7. بوابات القفل (Lock Gates)

- لا يُثبت عدد البوابات داخل الواجهة.
- تقرأ الواجهة القائمة من `GateReport` الخاص بإصدار المنهجية المستخدم.
- كل بوابة تعرض: الاسم العربي، `gate_code`، الحالة، الأدلة، سبب الفشل، revision الذي قُيمت عليه، الإجراء المطلوب إن وجد.

**الحالات المعروضة:** `PASS`, `FAIL`, `NOT_APPLICABLE`

**عرض مبسط:** `8 اجتازت | 2 فشلت | 1 غير منطبقة` مع التنبيه: "هذا ملخص للبوابات وليس درجة ثقة."

# 8. الواجهات الرئيسية (تفاصيل تنفيذية)

## 8.1 الرئيسية — مركز الانتباه

ترتيب الأولويات:
1. **يحتاج انتباهك:** مراجعات معلقة، تعارضات مفتوحة، نتائج أصبحت `STALE`، تشغيلات توقفت، نتائج تحتاج Revalidation، مصادر تنتظر Admission، تنبيهات النقاء المنهجي.
2. **أبحاث جارية:** آخر Research Runs وحالتها.
3. **استئناف العمل:** آخر Checkpoints القابلة للاستئناف.
4. **تغيرات حديثة:** النتائج، القرارات، والمنهجيات التي تغيرت.
5. **ملخص تشغيلي:** بعد الإجراءات المهمة.
6. **مركز الإعداد والتوجيه:** للمستخدم الجديد مع أمثلة توضيحية باستخدام `{ن ش ز}`.

## 8.2 واجهة «اسأل لسان» — المحادثة الميسّرة

### بنية الإجابة
كل جواب يحتوي:
- ما ثبت ضمن الملف الحالي.
- ما تدعمه الأدلة.
- الفرضيات الحالية.
- ما لم يُحسم.
- القيود.
- الخطوة البحثية التالية.
- المصادر والتشغيلات.

### حالة عدم كفاية الأدلة
**«الأدلة الحالية غير كافية لإصدار جواب محكوم.»** ثم يظهر: **«إنشاء بحث لهذه المسألة»**.

### القوالب الجاهزة الثلاثة

| القالب | الصيغة |
| :--- | :--- |
| **الجذر** | "ما الحالة الدلالية الحالية للجذر `{…}`؟ وإذا لم تثبت نواة جذرية، فبيّن ما هو معلوم وما بقي غير محسوم." |
| **المقارنة** | "قارن دلالياً بين `{…}` و`{…}` وفق الأدلة المحكومة، وبيّن المشترك والبقية المميزة والمواضع التي لا يزال التفريق فيها غير محسوم." |
| **السياق** | "حلل استعمال `{…}` في الآية `{…}` مع فصل مساهمة الجذر والصيغة والتركيب والسياق، وبيّن حدود الاستنتاج." |

### إكمال الآيات
- يعمل فقط من Corpus Snapshot مقبول ومحدد.
- يعرض: نص الآية، السورة والرقم، Corpus identity، النسخة.

## 8.3 مساحة الجذر

**التبويبات:** `نظرة عامة` | `المواضع` | `البنية` | `الفرضيات` | `الجيران` | `الأدلة المعارضة` | `الاختبارات` | `الجودة` | **`نقاء النتيجة`** | `التبعيات` | `التاريخ`

**حالة عدم وجود نواة:** **«لم تثبت نواة جذرية.»**

## 8.4 المختبر المعزول (Blind Lab)

- **وضع مستقل وواضح بصرياً.**
- يظهر أعلى الشاشة: **مختبر معزول — قبل القفل الداخلي**.
- يبدأ بالحالة: `UNKNOWN`.
- **قبل القفل:** تُحجب النتائج السابقة، Semantic Definition Registry، priors، owner answers، glossary/tafsir/dictionaries غير المسموح بها، post-lock comparison.
- **تحذير العزل:** **العزل سليم** أو **تم اكتشاف تلوث بالمعرفة السابقة — لا يمكن القفل.** `PRIOR_CONTAMINATED`.
- **سير المختبر:**
  ```text
  Corpus → Observations → Structure → Hypotheses → Negative Boundary → Falsification → Lexical Differentiation → Counterevidence → Gates → Internal Lock
  ```
- **بعد القفل:** يصبح **مقارنة النتائج السابقة** متاحاً في مساحة منفصلة.

## 8.5 عارض الفصل الطبقي

يعرض المعادلة الكاملة:
```text
ROOT + FORM/MORPHOLOGY + CONSTRUCTION/SYNTAX + ARGUMENT SEMANTICS + CONTEXTUAL FACE = LOCAL MEANING
```

## 8.6 واجهة المطور والخبير — الحوكمة

### 8.6.1 مركز الحوكمة الموسع

**أ. مستودع القواعد والسياسات**
- قائمة شاملة بكل قاعدة مؤثرة في عملية الاستدلال.
- تصنيف: منهجية، تقنية، سلطوية، سياقية.
- حالة القاعدة: نشطة، معلقة، مقترحة، تم إلغاؤها.

**ب. محرر القواعد والسياسات**
- واجهة JSON/YAML مع Validation.
- كل تعديل يُسجّل كـ **إصدار جديد** مع `Version Tag`.
- حقل إلزامي: **سبب التعديل** و **الأثر المتوقع**.

**ج. معاينة أثر التعديل (Impact Preview)**
- محاكاة التعديل قبل تطبيقه على جذر نموذجي مثل `{ن ش ز}`.
- تقرير الأثر يُظهر: الفروق في حالة القفل، البوابات التي تغيرت، الجيران المتأثرين، النتائج التي ستصبح `STALE`.

**د. سجل التغييرات التاريخي**
- من قام بالتغيير، متى، ما التغيير، لماذا، والأدلة المستندة إليها.
- إمكانية التراجع (Rollback) مع توثيق السبب.

**هـ. إدارة المصادر والقبول**
- تحديد المصادر المسموح بها (معجمات، تفاسير، دراسات سامية).
- تحديد دور المصدر: اختبار مساعد، مرجع تاريخي، ممنوع.

**و. إدارة المهارات والأدوات**
- استعراض المهارات المثبتة مع إصدارها وبصمتها.
- إدارة الأدوات المساعدة (QAC, Validators) مع تحديد دورها.

**ز. كاشف النقاء المنهجي (Purity Detector Admin)**
- إعدادات الكشف (أبعاد، عتبات، مصادر مرجعية).
- سجل الفحوصات.
- تقارير النقاء.
- سياسة التعامل مع النتائج الملوثة.

**ح. لوحة تحكم الاختبارات والتحقق**
- تشغيل اختبارات الانحدار (Regression Tests).
- تقرير التحقق: الاختبارات التي اجتازت، التي فشلت، وسبب الفشل.

### 8.6.2 مختبر الفرضيات
يعرض المرشحين جنباً إلى جنب: `H1`, `H2`, `C0`.
- أبعاد المقارنة: التعريف، شروط النقض، المؤيدات، المعارضات، أصعب موضع، أقوى منافس، التغطية، مشاكل التجريد، الفصل عن الجيران، البوابات الفاشلة.

### 8.6.3 مختبر التفريق الدلالي
يعرض الجذر الحالي مقابل الجار الدلالي مع: ما هو المشترك، ما البقية المميزة، اختبار الاستبدال، أقوى lexical competitor، الشواهد المؤيدة والناقضة.

## 8.7 واجهة إدارة الحوكمة والمراجعة

- **قائمة المراجعة:** العناصر التي تحتاج مراجعة بشرية (`LOCK_INTERNAL_RESULT` بانتظار `OWNER_ACCEPTED`).
- **سجل القرارات:** تاريخ كامل لقرارات القبول/الرفض/التأجيل.
- **إدارة التعارضات:** عرض وحل التعارضات المنهجية (`OPEN_AUTHORITY_QUESTION`).
- **إدارة التغييرات:** مراجعة مقترحات التعديل مع `Impact Analysis`.
- **أوامر الوصي (Steward Commands):** استقبال ومعاينة أوامر التغيير قبل اعتمادها.
- **مسار الإصدار:** لا يمكن الإصدار دون توثيق `Methodology Version` و `Corpus Snapshot` و `Review Decision` واجتياز **بوابة النقاء المنهجي** (`Purity Gate`).

# 13. استراتيجية الاختبارات

## Fixtures الاصطناعية
تتضمن:
- نتيجة مكتملة بنيوياً.
- فرضية مع C0.
- فشل Gate.
- `LOCK_BLOCKED`, `UNKNOWN`, `REJECTED`, `STALE`.
- `PRIOR_CONTAMINATED`.
- Review required, Owner decision required.
- **نتيجة ملوثة منهجياً (HERITAGE_BIAS_SUSPECTED).**

## `{ن ش ز}`
- لا يُستخدم كـfixture يتوقع تعريفاً دلالياً.
- يُستخدم فقط لاختبار عرض `LOCK_BLOCKED / NOT_ESTABLISHED`.

# 14. معايير القبول الشاملة (27 معياراً)

يعد UI/UX ناجحاً عندما يثبت أن:

1. كل ادعاء يمكن تتبع مصدره ودليله وRun الخاص به.
2. UNKNOWN ظاهر وغير مخفي.
3. Counterevidence ظاهر وغير ثانوي.
4. الحالات المعرفية والمراجعة والحداثة والنشر منفصلة.
5. لا توجد نسبة واحدة توصف بأنها احتمال صحة.
6. بوابات القفل تأتي من العقد لا من hard-coded frontend logic.
7. Blind Lab لا يكشف priors قبل القفل.
8. Derived views لا ترفع السلطة.
9. المستخدم لا يستطيع تنفيذ انتقال غير مصرح به.
10. Steward يعرض Preview قبل التغيير.
11. التغيير الحاكم يمر عبر Change Proposal.
12. corpus غير المقبول لا يستخدم في تشغيل علمي.
13. STALE لا يعرض كحقيقة حالية.
14. الإبطال قابل للتتبع.
15. إعادة الإنتاج مرتبطة بـrevision والمنهجية وcorpus.
16. الرسوم لها بدائل نصية/جدولية.
17. جميع الشاشات الأساسية تعمل RTL بشكل أصيل.
18. لا يعتمد البحث أو الاستئناف على ذاكرة المحادثة فقط.
19. يمكن للمستخدم الجديد فهم الأساسيات عبر Onboarding Launchpad.
20. مفتش الاعتماديات يُظهر التأثير المتعدي بوضوح.
21. **كاشف النقاء المنهجي يعمل ويمنع نشر النتائج الملوثة (`Purity Gate`).**
22. **تقرير النقاء يُظهر الأبعاد الثمانية مع أسباب وتوصيات لكل بُعد.**
23. يمكن للمستخدم التبديل بين مستويات العرض الثلاثة دون فقدان السياق.
24. جميع المكونات الرئيسية تجتاز اختبارات Accessibility.
25. النظام يحافظ على أداء مقبول تحت 100 مستخدم متزامن.
26. يمكن استئناف Research Run من أي مرحلة.
27. كل تغيير حاكم يُسجل في Audit Log مع الأثر الكامل.

# 16. القرار النهائي

التجربة المستهدفة لـLisan هي:

> **Research Workspace + Evidence System + Epistemic State + Governed Runtime + Human Review + Knowledge Memory + Governance Control Plane + Purity Assurance.**

والمحادثة هي نقطة دخول سهلة فوق هذه الطبقات، لا طريقاً مختصراً يتجاوزها.

**المعيار التصميمي الأعلى لكل واجهة:**

> **«كل ادعاء يراه المستخدم يجب أن يستطيع أن يسأل عنه: ما حالته؟ لماذا؟ ما دليله؟ ما الذي يعارضه؟ هل هو نقي منهجياً؟ من راجعه؟ ما الذي يعتمد عليه؟ وما الذي يمكن أن يبطله؟»**

**هذه الوثيقة هي النواة المعتمدة لبناء تطبيق لسان من الصفر.**
